# 模块记忆维护

先读 `AGENTS.md`。只沉淀已核实的实现与已获用户采纳的方案；用户要求更新记忆即授权维护相关文档。v3 重构已完成，当前源码和测试是实现事实源，`项目文档.md` 是旧版 2.7.0 存档。

## 位置与索引

| 类型 | 位置与命名 |
| --- | --- |
| 模块关系与状态链 | `memories/<模块>/00-模块地图.md`；需要拆分时用 `NN-<主题>.md` |
| 缺陷的现象、根因与修复 | `memories/bugs/MEM-<n>-<主题>.md`，沿用现有编号且不复用 |
| 单组件或能力 | 归属模块目录；只有确有跨文件机制或隐蔽约束时单独立档 |

模块名使用当前职责，如 player、plaza、playlist、origin_sdk、db；通用组件需要独立沉淀时可归 core。现有 db 目录覆盖 `lib/data/` 的持久化链，不为路径整齐改动既有索引。

每篇登记到本目录 `README.md`；新目录建立覆盖范围与索引表，并登记到上层 `README.md`。根索引是 `memories/README.md`。记忆不会自动加载，入口必须能引导下一位 agent 找到它。

## 写什么

以“组件和文件之间的关联”作为主体，按主题组织以下内容，可合并相邻段落：

- 一句话模型、配置/入口、核心文件职责。
- 谁调用谁、谁持有状态、谁读写数据、谁渲染结果；使用简明关系图或表格。
- 关键状态、数据与失败/恢复链。
- 易踩坑：现象 → 条件 → 根因 → 当前处理；保留可复用约束，避免逐行解读。
- 症状对应的排查入口，以及会变化的路径、符号、参数和接口。
- 核对日期与源码基线；未展开的部分和未做的线上/真机验证明确说明。

## 更新旧结论

- 对照当前实现和测试取证，不因旧记忆写着“实测”就沿用。接口风控、榜单可用性、平台适配尤其需要重新核对。
- 区分历史根因和当前约束；例如曾经“缺 cid 必然失败”，在 SDK 已补齐 cid 后应标为历史行为，同时保留合集先分流的语义要求。
- 修改模块地图后同步各层索引摘要和相关缺陷互引；保留仍然成立的陷阱及原修复提交，不覆写成没有发生过。
- 不复制旧版全景，不把测试通过写成接口在线可用，不固定用例数量或 analyze 的动态结果。
- 不恢复已退休的重构计划或原型依赖。UI 以当前 `lib/core/` 和 `lib/features/` 实现为参照。

## 引用与校验

路径用仓库相对路径；保留既有换行符。新写互引用标准 Markdown 相对链接，已有 wiki 链接更新时可一并改为可解析链接。

交付前检查文档已登记、所有本地链接和关键源码路径存在、重命名引用已同步，并搜索本次淘汰的旧结论。仓库没有常驻记忆校验脚本，可用临时只读检查完成；无需为文字修改新增业务测试。
