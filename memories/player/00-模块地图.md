# player · 模块地图

> 全景（启动流程/模式矩阵）见 `项目文档.md` 第 5 章；本文只补**引用关系**与**易踩坑**。基线 0aac7bb / 2.7.0，2026-10-24 核对。

## 一句话模型

BBPlayer 持有 just_audio 实例并完成「切歌决策」，AudioPlayerHandler 把状态桥到系统媒体会话，PlayerModel 给 Widget 层做只读转发；播放队列不是一个结构，而是「`playerList`（待播放列表，内存+DB 双份）+ 歌单表 prev/next 链」两个来源按播放模式现场裁决。

## 引用关系（谁持有谁）

```
main.dart ──new──> AudioPlayerHandler(_playerHandler 全局)
    │ AudioService.init 返回的 playerService 与 _playerHandler 是同一实例
    ▼
PlayerModel.init(playerHandler, playerService)     [model.dart]
    └─ 持有 handler，几乎所有方法转发 handler / handler.player(BBPlayer)

AudioPlayerHandler [service.dart]
    ├─ final BBPlayer player = BBPlayer()   ← 组合，handler 是 BBPlayer 唯一正式入口
    ├─ 订阅 audio.playbackEventStream / playerStateStream / positionStream / durationStream
    └─ playerStateStream 每次变化：_broadcastState() → eventBus.fire(ScrollLyric())

BBPlayer [instance.dart]
    ├─ final audio = AudioPlayer()（just_audio）
    ├─ MusicItem? current；List<MusicItem> playerList（与「待播放列表」DB 表互为镜像）
    ├─ AutoCloseMusic autoClose（定时关闭）
    └─ _play() → 本地：audio.setFilePath(localPath)
                 在线：audio.setAudioSource(BBMusicSource(music))

BBMusicSource [source.dart]
    ├─ extends StreamAudioSource（just_audio）
    ├─ 命中缓存：flutter_cache_manager("bbmusicMediaCache") 读文件，key = "<origin>-<id>"
    ├─ 未命中：service.getMusicUrl(id)（origin_sdk）→ http 流式拉取 → _bytes 全量内存累积
    └─ onDone 落盘缓存；下载模块（download/model.dart）复用同一 cacheKey
```

关键点：**BBPlayer 直接读写 DB**（queryByParam/queryRandom/update），不走任何 Repository；UI 层也直接 `new DBOrder()` 读库——这是数据层的隐式契约。

## 切歌决策链（`BBPlayer.play`）

换歌四条件任一满足即切：`current == null` / `orderName 不同` / `playId 非空且不同` / `id 不同`；否则视为「点同一首」→ 播放中暂停、暂停中续播。⚠️ 判定顺序有讲究：`playId` 空串（本地库旧行、广场未入库条目）时退化为按 `id` 判等。

`endNext()`（自然播完也走这里，Throttle 1s）：
- signalLoop → seek(0) 重播
- random → `db.queryRandom(orderName)`
- listOrder / listLoop → **`playerList` 非空时待播放列表优先**：listOrder 按 `playerList.indexWhere(playId)` 取下家（isLast 提示到底）；listLoop 按 `current.next` 在 playerList 找，找不到回第一首。playerList 空才走歌单表 `current.next` 链。
- ⚠️ 切歌前先 `queryByParam` 重新读当前行的 prev/next，与内存比对——歌单增删后链表已变，这是「链表漂移」的自愈手段。

## 待播放列表的双重身份

`addPlayerList()` 流程：内存 `playerList.addAll`（每首新 `playId = uuid`，`orderName = 待播放列表`）→ **`db.deleteAll` 全表清空 → 逐条 insert → `getUpdatedMusicList` 重建链表 → 整体覆盖内存列表**。所以待播放列表的顺序真相在 DB 的自增 `id` 里，内存列表每次全量重建。1000 首上限即源于全量重写的成本。

## 易踩坑（⚠️ 已实证）

1. **启动清空待播放表**：`main()` 里 `db.deleteAll(TableName.musicWaitPlay)` 先执行，`BBPlayer._initLocalStorage()` 再读该表必为空 → 待播放列表不跨启动。两处逻辑矛盾（项目文档 12.5）。
2. **节流 Timer 单位写错**：`_updateLocalStorage()` 用 `Duration(microseconds: 500)`（0.5ms），形同虚设（12.9）。
3. **`play()` 尾部 duration 回写**依赖 `current!.duration == 0`，若 `current` 为 null 会空指针崩溃（`play()` 无参且 playerList 为空路径下 current 仍为 null 时直达该行）。
4. **`_initLocalStorage` 的 `addPlayerList(playMusics)`** 会把空列表也走全量重写流程（EasyLoading 闪一下）。
5. **BBMusicSource 内存全量缓冲 + 300ms 轮询等数据**（12.3）：长音频内存峰值 = 整首歌；网络分支未声明 `rangeRequestsSupported`，未缓冲区 seek 可能失败。
6. **`PlayerModel.togglePlayerMode(mode)` 参数被丢弃**：转发时没把 `mode` 传下去（model.dart:87-90），传参调用等于无参调用。

## 易腐字段（改这里时同步更新本文）

- `music2cacheKey` = `"${origin.value}-${id}"`（source.dart，下载模块共用）
- `AutoCloseMusic.openPlayDoneAutoClose` 双开关语义
- 播放模式持久化用 `value`（1~4），toggle 顺序 signalLoop→listLoop→random→listOrder 与枚举声明顺序不一致
